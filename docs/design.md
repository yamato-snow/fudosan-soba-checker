# 設計メモ

このツールが「なぜこの作りなのか」を残す。判定ロジックは README の「判定の読み方」が仕様、
ここはその**根拠**（何を試して、何が駄目で、何を選んだか）。

## 解こうとしている問題

不動産の掲載価格を見ても、それが高いのか安いのか分からない。近傍の実取引と比べたい。
国交省の不動産情報ライブラリ（reinfolib）が実取引データを公開しているので、
これを取り込んで「対象物件の㎡単価が、似た事例の分布のどこにいるか」を出す。

制約として最初に決めたこと:

- **推定モデルを作らない**。データ量が小さく、当たっているのか検証できないものを信じない
- **分布をそのまま見せる**。中央値・四分位・使った件数を必ず出し、条件を緩めたなら緩めたと書く
- **判定できないときは判定できないと言う**。無理に数字を出さない

## Phase 0: 座標での近傍抽出は使えなかった

最初は「自分の位置から半径 N km」で近傍を取る設計だった。XPT001（地図タイルAPI）で
実データを取って確認したところ、**返ってくる座標が数km級のクラスタ点**で、
個別取引の位置ではなかった。半径での絞り込みは成立しない。

→ **XIT001（市区町村コード指定）＋「地区リング」方式**へ設計変更した。
距離の代わりに行政区画の入れ子で近さを定義する:

| リング | 範囲 |
|---|---|
| Ring0 | 同一地区（対象物件の DistrictCode） |
| Ring1 | 近隣地区（生活圏。手動設定 or 地価類似で自動推定） |
| Ring2 | 基準市全域（`TARGET_CITIES` の先頭） |
| Ring3 | 対象市全域（`TARGET_CITIES` すべて） |

「動かしてから決める」ためのプローブが `scripts/phase0_probe.py`（記録として残置）。

## データの扱い

- API の `UnitPrice` は使わず、**㎡単価は自前計算**（土地=価格÷土地面積 / 戸建=価格÷延床面積）
- レコードに一意IDが無いので、内容ハッシュ（時期・地区・種別・価格・面積・築年）を
  UNIQUE キーにして**冪等 upsert**。取込バッチは何度流しても増えない
- API は 1req/秒スロットル＋指数バックオフで叩く

## 判定ロジック（Lv1）

事例の㎡単価の**中央値**を相場とし、対象物件との乖離%を主表示。同じ標本の四分位で
3段バンド（Q1未満=割安 / Q1〜Q3=適正 / Q3超=割高）を補助表示する。
事例が5件に満たなければ抽出条件を段階的に緩め、緩めたぶん信頼度を下げる。

回帰やスコアリングを載せていないのは、**1地区あたりの取引が中央値3件しかない**ため。
この密度では係数が安定せず、精度が上がったかどうかも検証できない。

## 改善: 中古戸建の判定が「緩すぎて無害化」していた問題

実データで検証したところ、中古戸建の判定は 0件ではなく**何を入れても「適正」に落ちる**状態だった。
原因は3つあり、それぞれに対処した。

### 1. 比べる軸と絞る軸がズレていた（本丸）

主指標は**延床単価**なのに、事例の絞り込みは**土地面積±30%のみで延床は無条件**だった。
結果、延床40㎡と180㎡が同じ母集団に入り、㎡単価が 33,000〜900,000円/㎡ まで暴れていた
（延床が小さいほど土地値が薄い延床に乗るので単価が跳ね上がる）。

→ **戸建は延床でも絞る**。土地の判定が相対的に当たっていたのは、絞る軸（土地面積）と
比べる軸（土地㎡単価）が一致していたからで、戸建だけこの一致が崩れていた。

拡張段階は種別ごとに分ける。延床は **±50% を下限として撤廃しない**
（撤廃すると今回直した壊れ方に戻る。±50%でも足りないなら「判定できない」と返す方が誠実）。

| 段 | ring | 築年 | 土地面積 | 延床 |
|---|---|---|---|---|
| 1 | 1 | ±5 | ±30% | ±30% |
| 2 | 2 | ±5 | ±30% | ±30% |
| 3 | 3 | ±5 | ±30% | ±30% |
| 4 | 3 | ±10 | ±30% | ±30% |
| 5 | 3 | ±10 | ±30% | ±50% |
| 6 | 3 | 無制限 | ±30% | ±50% |
| 7 | 3 | 無制限 | ±50% | ±50% |

リング拡大を条件緩和より先に置くのは、**似ていない事例で件数を稼ぐより、
範囲を広げて似た事例を探す方が正しい**から。

### 2. 「古家付き土地」相当の外れ値が分布の裾を伸ばしていた

延床45㎡・150万円のような、実質「古家付き土地」の取引が Q1〜Q3 を押し広げ、
バンドが機能しなくなっていた（Q3/Q1 が 2.2倍）。

「古家＝延床◯㎡未満・築◯年超」のような**意味的な除外ルールは作らなかった**。
掲載情報なしに古家か否かは判別できず、恣意的な閾値が新しい歪みになるため。
代わりに統計的に処理する:

- 第1防壁 = 上の延床フィルタ（延床45㎡は105㎡ターゲットの±50%にも入らない）
- 第2防壁 = **IQR トリム**。`[Q1−1.5×IQR, Q3+1.5×IQR]` の外を除外して中央値・四分位を再計算。
  標本が6件未満のときは適用しない（四分位フェンス自体が不安定なため）
- **5件の閾値判定はトリム後の件数**で行う（「使える事例5件」を保証する）。除外件数は必ず表示する

### 3. Ring1 が死んでいた

近隣地区は手動設定（`NEIGHBOR_DISTRICTS`）前提だったが、未設定だと **Ring1 = Ring0** になり、
同一地区の次がいきなり市全域だった。リングの刻みが実質2段しかない。

→ 未設定時は **同一市内で宅地(土地)㎡単価の中央値が対象地区の±25%以内**（双方3件以上）の地区を
Ring1 として自動推定する。座標が使えない環境で「近い」の実用的な代理は「土地の値段水準が近い」であり、
取込済みデータだけで計算できる。手動設定があれば**常にそちらが勝つ**（生活圏の定義は人間の方が正しい）。

### 4. ばらつきが大きいままの「適正」を信頼度に反映する

トリム後でも標本が散らばっているなら、バンド判定の意味は薄い。
最終標本の **Q3/Q1 > 1.8** のとき信頼度を1段下げ（A→B→C）、「ばらつき大」を表示する。

## 効果測定

実データ約2,300件に対し、同一標本で改善前後を比較した（各種別150件を等間隔サンプリング）。

**あるケース（土地180㎡・延床105㎡・築2001年・2,500万円）**

| 指標 | 改善前 | 改善後 |
|---|---|---|
| 事例の延床レンジ | 40〜180㎡ | 85〜135㎡ |
| Q3/Q1 | 2.22倍 | 1.09倍 |
| 中央値比 / バンド | +13.6% / 適正 | +74.0% / 割高 |
| 信頼度 / 最終リング | C / 市全域 | A / 近隣地区 |

無害化していた「適正」が「割高（+74%）」に反転した。

**疑似ターゲット計測（各150件）**

| 指標 | 土地 | 中古戸建 |
|---|---|---|
| 信頼度A | 28.7% → 57.3% | 15.3% → 24.0% |
| 市全域以上まで拡大 | 67.3% → 28.7% | 78.7% → 72.0% |
| Q3/Q1 の中央値 | 1.66 → 1.52倍 | 1.58 → 1.53倍 |

戸建のリング拡大率の改善が小幅なのは、延床フィルタが母集団を正しく削るぶん拡大が起きやすくなるため。
**副作用ではなく設計どおりの挙動**で、信頼度Aは 15.3%→24.0% と改善している。

## 区分マンション対応（A-1）: 実データで確認した前提

投資判断拡張のために「中古マンション等」を対象種別に加えた。**コードを書く前に**
XIT001 の実レコードを1四半期ぶん取って前提を確認した（`scripts/phase_a1_probe.py`。
出力は `out/phase_a1_condo_*.json`＝gitignore 済み）。区分12件で観測した事実:

| 項目 | 観測結果 | 設計への反映 |
|---|---|---|
| `Area` | 55〜90㎡（中央値75）。土地面積の桁ではない | **専有面積**として扱い、㎡単価＝総額÷`Area`（土地と同じ式） |
| `TotalFloorArea` | **12件すべて空** | **延床フィルタを区分に適用しない**（適用すると必ず0件） |
| `BuildingYear` | 12/12 充足 | 築年フィルタは戸建と同様に効かせる |
| `Structure` | ＲＣ 10件 / ＳＲＣ 2件（全角） | B-2 の耐用年数で使う語彙。A-1 では未使用 |
| `DistrictCode` | 12/12 充足 | 地区リングがそのまま効く |
| `UnitPrice` / `PricePerTsubo` | 0/12（空） | 従来どおり API の単価は使わず自前計算 |
| `Region` | 全件空（土地・戸建は「住宅地」等が入る） | 保存はするが判定には使わない |

**区分の㎡単価は土地と同じ「総額÷`Area`」**になる。戸建だけが「総額÷延床」で、
区分は `Area` 自体が専有面積なので比べる軸と絞る軸が最初から一致している。
`land_unit_price`（従指標）は区分では主指標と同値になる。

段階拡張は種別ごとの3本目 `EXPANSION_STAGES_CONDO` を持つ。延床の段が無いぶん戸建より短い:

| 段 | ring | 築年 | 専有面積 |
|---|---|---|---|
| 1 | 1 | ±5 | ±30% |
| 2 | 2 | ±5 | ±30% |
| 3 | 3 | ±5 | ±30% |
| 4 | 3 | ±10 | ±30% |
| 5 | 3 | 無制限 | ±30% |
| 6 | 3 | 無制限 | ±50% |

面積の緩和説明は種別で言葉を変える（土地・戸建＝「土地面積」/ 区分＝「専有面積」）。
`content_hash` のキーに `Type` が含まれるため、**DB を消さずに再取込するだけ**で区分行が増えた
（再取込2回で新規0件・合計2,975件のまま＝冪等を実データで確認）。

### 取込後の観測（疑似ターゲット150件）

事前に「同一マンション内の複数取引が事例に入って単価が近すぎ、`Q3/Q1` が 1.02 のような値になり
バンドが極端に狭くなる」リスクを想定していた（reinfolib は建物名を返さないため機械的に区別できない）。
**実データでは起きなかった**ので、ばらつき小フラグは作らない:

| 指標 | 土地 | 中古戸建 | 区分（新規） |
|---|---|---|---|
| 信頼度A | 57.3% | 24.0% | **61.3%** |
| Q3/Q1 の中央値 | 1.52倍 | 1.53倍 | **1.39倍** |
| Q3/Q1 < 1.05 の割合 | — | — | **0.0%**（最小 1.07倍） |

区分の信頼度Aが最も高いのは、専有面積という比べる軸と絞る軸が最初から一致していて、
かつ1地区あたりの取引密度が戸建より高いため。**閾値を先に作らないという判断が正しかった**ことを
実データが示した形なので、この観測を残しておく。

## 賃料相場（A-2）: 同じエンジンに載せる

用途が自宅探しから投資に広がると、買値の妥当性だけでは判断できない。本題は
「借りて・返して・回して、税引後に手元へ残るか」で、その一段目が**いくらで貸せるか**になる。

### データ源は手入力／CSV しかない

国交省 API（XIT001）は**取引価格**であって賃貸ではない。賃貸サイトのスクレイピングは各サイトの
規約で禁止されている。したがって賃料の母集団は自分で入れるしかない。これは制約であって欠陥ではないので、
**薄い母集団を薄いまま正直に扱う**（後述の「あと N 件」）方向で設計した。

### 統計の芯は1文字も変えない

`evaluate()` / `trim_cases()` / `quartiles()` / `band_for()` / `_confidence()` は**無変更**。
賃料側でやったのは3つだけ:

1. **主指標を差し替える** — `(monthly_rent + admin_fee) ÷ exclusive_area`（円/㎡/月）。
   管理費を足すのは、募集情報の賃料/管理費の切り分けが恣意的で、同じ実質額を「8.0万＋0.5万」とも
   「8.3万＋0.2万」とも書けるため。売買側で `UnitPrice` を使わず自前計算しているのと同じ思想
2. **段階拡張の並びを賃料用に持つ** — 面積の軸は `floor_tolerance`（区分=専有／戸建=延床）に載せ、
   `area_tolerance`（土地面積）は全段固定。借り手は敷地の広さで賃料を決めないので、土地面積では絞らない。
   `Criteria.floor_label` を足して緩和説明が「専有面積を±50%に緩和」と出るようにした
   （既定値が現行文言と同じ「延床」なので、売買側の表示も既存テストの期待文字列も変わらない）
3. **㎡単価に面積を掛けて月額に戻す** — 出力は想定月額賃料レンジ（Q1〜Q3 × 面積）

`Case` に足したのは `source: object | None = None` の1つだけ。判定には一切使わず、
`Valuation.cases` から `RentCase` を取り戻して賃料の語彙（賃料・管理費・間取り・階）で表示するためだけに持つ。
テーブルは `rent_listings` で `transactions` とは**別**（混ぜると単位の違うものが同じ中央値に載る）。
地区リングの WHERE 条件だけは `_ring_filter(ctx, ring, model=...)` でモデルを差し替えて共有する
（Ring2 の OR ロジックを複製すると片方だけ直す壊れ方をするため）。

### 作らなかったもの と その理由

| 作らなかったもの | 理由 |
|---|---|
| 成約賃料への補正係数 | 係数の妥当性を検証する手段が無い。`status` 列で区別し、表示で注記するだけにした |
| 事例の鮮度による減衰重み・信頼度降格 | 同上。恣意的な係数を統計の芯に入れない。代わりに**最終標本の調査時点の年レンジを必ず表示**して、古さの判断を人間に返す |
| `MIN_CASES` の引き下げ | 3件の中央値を相場とは呼ばない。判定不能は「データが薄い」という事実の正しい写像 |
| 取込の洗い替えモード | `purge_rent_source(source_ref)` → 再取込で足りる。分岐を増やさない |
| e-Stat の公的統計を参考値として並べる | 住宅・土地統計調査の家賃は都道府県／人口規模別が中心で地区粒度が無い。仮に市区町村粒度があっても、住宅ストック全体を均した平均家賃は「地区リング×物件条件で絞った事例分布」と比較可能な数字ではなく、判定枠の外に置いても「近い数字」と誤読される害の方が大きい |

### 判定不能を突き返さない

`MIN_CASES=5` を下げない代わりに、判定できないときは
**「あと N 件登録すると判定できます」＋ `/rent/import` への導線**を必ず出す。
薄い母集団を埋める現実的な経路はこれしかなく、正直さ（判定できないと言う）と
実用性（じゃあどうすればいいか）を両立できる唯一の形として選んだ。

### 取込は部分成功が原則

1行の書き損じで30行の入力をやり直させると母集団が育たない。不正行は**行番号つき**で一覧に出し、
正常行はそのまま取り込む。入ってくる汚れ方（`cp932`／BOM／全角数字／`"85,000"`／`62.5㎡`／
`徒歩8分`／空行／`#` コメント行）はパーサ側で吸収する。冪等キーは内容ハッシュ（`source_ref` を含む）で、
売買側 `content_hash` と同じ作法。

## 意図的に作っていないもの

- ヘドニック回帰・機械学習（データ量が足りず、精度を検証できない）
- 掲載サイトのスクレイピング、レインズ連携（賃料も同じ。手入力／CSV が唯一の道）
- 座標・ポリゴンによる地理的な近傍判定（Phase 0 で不可能と確定）
- 認証・マルチユーザー・PostgreSQL 移行（ローカル単独利用のため不要）
